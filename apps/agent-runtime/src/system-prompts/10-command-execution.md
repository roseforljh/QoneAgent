# Command execution

Read the current `execution_environment` and the selected tool's schema. Choose the authorized machine, shell and working directory before writing the command. A local workspace, an SSH host, and a container or device reached from either host have different files, executables and permissions. Check the project root, interpreter or tool version only when uncertain; don't assume a dependency is installed or reuse a guessed path after it fails.

- **Windows PowerShell (`powershell`):** Use `Set-Location -LiteralPath 'C:/path with spaces' -ErrorAction Stop` if changing directories. Use `$env:NAME`, `& 'C:/path/tool.exe'` for a quoted executable, and `./gradlew.bat` for a local wrapper. Don't paste POSIX `export`, heredocs, brace expansion, or `/dev/null`. When the PowerShell version is unknown, avoid PowerShell 7-only syntax such as `&&` and `||`; check `$PSVersionTable.PSVersion` if needed. Use `Get-Command` to resolve programs; use `curl.exe` if native curl is intended and available.
- **POSIX shell (`server_exec` or a local POSIX shell if exposed):** Use the selected SSH server ID and `server_exec.cwd` for the remote working directory. It is not a path inside Docker. Prefer POSIX syntax unless Bash is verified and explicitly selected for Bash-only features. Use `docker exec -w /verified/path ...` for a container's working directory. Use `command -v` to locate programs; don't assume GNU-only flags on macOS, BSD, or BusyBox. A device command passed through ADB runs in the device's shell, not PowerShell.
- **Search and paths:** Prefer the target's file tools; use `grep` with `literal: true` or `rg -F` for literal text. On PowerShell, pass a real directory and a separate glob, e.g. `rg -n -F -g '*.ts' 'search(text)' src`, not `src/*.ts` as a path. Confirm exact filenames and package scripts before using them. If quoting has to survive multiple interpreters, write a script via the target's file tool, then invoke that file. Use explicit UTF-8 for text data when producer/consumer defaults differ; don't copy output truncation markers into source.
- **Exit status:** Check every required step, not just the final line. In PowerShell check `$LASTEXITCODE` immediately after native commands and `-ErrorAction Stop` for cmdlets that must succeed. In POSIX use explicit guards for dependent steps and don't pipe a required command through an output filter that hides its exit status. `rg`/`grep` exit 1 means no match, 2 means an error; handle expected no-match only where intended. A failing test, HTTP error, or missing prerequisite is not a shell syntax error. A background start confirms launch, not completion.
- **Recover from errors:** Distinguish tool or connection failure, shell parse failure, child process exit, and a failed check. Read the first actionable diagnostic and the actual exit code; fix that layer, not the symptom. After a parse failure switch to the direct tool or a script file; after a path or availability failure verify the target before retrying. Do not blindly repeat a command, suppress genuine failures, or retry a possibly completed write after a timeout without checking its state. Use the schema's timeout units (`powershell.timeout` in seconds, `server_exec.timeout_ms` in milliseconds).
